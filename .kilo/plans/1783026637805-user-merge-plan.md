# Merge Duplicate Platform Client (User) Accounts

## Goal
Consolidate duplicate platform client accounts (e.g. user `#67` and `#744` — both "Hossam Sakr", different emails) into a single survivor. The duplicate's child rows are reassigned to the survivor, conflicting scalar fields are resolved by an admin via a diff UI, and the duplicate is soft-deleted.

## Scope
- **In scope**: platform `users` rows. Tables holding `user_id` or `client_id` (where the FK targets `users.id`).
- **Out of scope**: ERP `tenant_clients` rows. Those are a separate entity living in the `erp_tenant_clients` table and are not part of this plan.

## Decisions (locked)
| Decision | Value |
|---|---|
| Survivor wins by default | Yes — survivor's values kept when admin accepts "use survivor" |
| Field-level diff | Yes — admin picks per conflicting field (survivor | duplicate | merge) |
| Where triggered | Admin UI action on user profile page **and** `php artisan users:merge` |
| Post-merge duplicate state | Soft-delete (`deleted_at` set, row preserved for audit) |
| Pre-existing duplicate `user_id` UNIQUE collisions | Handled per-table (skip or reassign to survivor) |
| Audit | `AdminAuditLog` entry: "Merged user {duplicateId} into {survivorId} by admin {id}" |

## Affected tables (sample; full list produced by scanning `Schema::getColumnListing()` at runtime in the service)

Direct FK to `users.id` (`user_id` or `client_id`):
- `invoices.user_id`, `projects.user_id`, `transactions.user_id`, `user_loans.user_id`
- `wallets.user_id`, `user_devices.user_id`, `user_subscriptions.user_id`, `subscriptions.user_id`
- `tickets.user_id`, `user_threads.user_id`, `user_threads.peer_id`
- freelance: `freelance_jobs.client_id`, `freelance_jobs.freelancer_id`, `proposals.freelancer_id`, `reviews.client_id`
- tours/onboarding: `tour_progress.user_id`
- audit columns (do NOT reassign — keep historical actor): `created_by`, `updated_by`, `kyc_verified_by` — **only reassign `created_by` if explicitly required by admin; default: leave alone**

Pivot / linking tables (handled carefully to avoid UNIQUE collisions):
- `tenant_clients.user_id` (`user_id` is nullable there — set duplicate's rows to survivor; the FK is 1:1-per-user by convention but nullable)
- role/permission tables: `model_has_roles`, `model_has_permissions`, `personal_access_tokens`

## Deliverables

### 1. Service — `app/Services/UserMergeService.php`
- Public API:
  - `preview(int $survivorId, int $duplicateId): array` — returns conflicts, child counts, dry-run report (no writes).
  - `merge(int $survivorId, int $duplicateId, array $resolutions, int $adminId): void` — transactional merge.
- Steps inside `merge`:
  1. Lock both `users` rows with `SELECT ... FOR UPDATE`. Reject if either is soft-deleted or same id.
  2. Apply `resolutions` for scalar fields (`name`, `email`, `phone`, `country`, `city`, `mobile_1`, `mobile_2`, `telegram_username`, `whatsapp_number`) — only write if resolution differs from current survivor value.
  3. For each affected child table:
     - `UPDATE child SET fk_col = survivor WHERE fk_col = duplicate`
     - For tables with a UNIQUE(other_col, user_id) constraint: detect collision first (`SELECT id WHERE other_col=? AND user_id=survivor`); policy = `skip` (the duplicate's row stays, moved to survivor on next pass after admin resolves). Document this in the audit log.
  4. Reassign role/permission rows (merge + dedupe).
  5. Personal access tokens of duplicate → soft-delete (`revoked`) to force re-login as survivor.
  6. Soft-delete duplicate user with `deleted_at = now()`.
  7. Write `AdminAuditLog` entry with full diff snapshot (JSON column).
  8. Wrap everything in `DB::transaction()`; on any throw, rollback is automatic.

### 2. Artisan Command — `app/Console/Commands/MergeUsersCommand.php`
- Signature: `users:merge {survivor} {duplicate} {--dry-run} {--field=*} {--yes}`
- Validates: both ids exist + not soft-deleted; emails differ (warn if not); prints a field-by-field diff and asks for `--field name=survivor` style resolutions, or interactive prompt if `--yes` not passed and stdin is a TTY.
- On `--dry-run`: calls `preview()` only, prints summary, exits 0 with no writes.

### 3. Admin UI
- Routes (under existing admin prefix):
  - `GET  /admin/users/{user}/merge`           → form to pick the duplicate
  - `POST /admin/users/{user}/merge/preview`   → returns diff JSON / reloads with conflicts
  - `POST /admin/users/{user}/merge/confirm`   → applies merge
- Add "Merge into another client" button on `resources/views/admin/users/show.blade.php` (or admin layout for the users section).
- A simple diff page: side-by-side fields with radio buttons (Keep survivor | Use duplicate) for each conflict.
- Gate with `Gate::define('merge-users', fn($admin) => $admin->can('users.update'))` (or existing equivalent policy). Use existing `UsersController` patterns.

### 4. Tests
- `tests/Feature/UserMergeTest.php` covering:
  - Dry-run reports counts but makes zero writes (assert row count delta = 0).
  - Merge reassigns `invoices`, `projects`, `transactions` to survivor.
  - Merge soft-deletes duplicate with `deleted_at` set.
  - Duplicate-row UNIQUE collision is reported and skipped without throwing.
  - Audit log entry exists with both ids.
  - Repeat merge on already-merged duplicate is rejected.

## Risks
- **Hidden FKs**: a child table not in our list could throw FK violation at commit. Mitigation: service lists affected tables via a single `Schema::getTables()` + introspection; unknown FKs surface as SQLSTATE[23503] which we catch and surface as a clear error.
- **Audit columns**: reassigning `created_by` would erase authorship. Default: leave audit `*_by` columns alone.
- **Single-session tokens**: tokens of the duplicate are revoked so the user is forced to log back in as the survivor.

## Out of Scope (explicit)
- ERP `tenant_clients` rows merge.
- Merging platform users whose tenants already have `tenant_clients` rows pointing at both — surfaced in `preview()` as a warning only, not auto-resolved.
